**Phase 3 notes (implemented)**:
- Red run (test commit): 96 scenarios, 6 passed / 90 failed; the passing ones exercised the T004/
  T005 foundations or negative cases. Green: every `@xen_005` scenario and the full suite.
- Ports differ from the plan's list where the layering asked for it: `AuthorizeInBrowser` (one
  webservice opens the loopback listener first — so a busy port fails before the browser opens —
  then the browser, and waits; `open_browser` + `await_oauth_callback` in the plan),
  `ExchangeOAuthToken`/`RefreshOAuthToken` (oauth2 webservice), `SignAwsRequest`,
  `AnswerDigestChallenge` (`ReadChallenge` + `Answer`), `Find/SaveDigestState` (ui_state
  persistence) and `LockOAuthToken` (vault persistence: one mutex per owner, the single-flight
  refresh). Tokens are read from the vault and written through the services' vault writer (the
  same path as secrets), so no separate token persistence ports exist.
- `ManageOAuthService` (`OAuthService` binding): `GetNewToken`/`Refresh` take `{ local_id,
  owner_id, auth? }` — `auth` is the editor's (possibly unsaved) OAuth 2.0 configuration; without it
  the owner's saved auth is used. An unsaved request owns its token by tab id. Codes beyond the
  contract: `OAU-08499` cancelled, `OAU-09500` browser could not open, `OAU-10404` no token,
  `OAU-11503`/`OAU-12503` token endpoint unreachable/unreadable, `OAU-13400` unparsable callback,
  `OAU-14400…20400` controller validation, `AWS-0x`, `DIG-0x`.
- Send: the effective auth owner is the request or the folder/collection whose auth it inherits.
  Before scripts, an expired OAuth token is refreshed under the owner lock (re-read first, so a
  concurrent send uses the fresh token) or the send fails with `SND-07409` (detail `owner_id`)
  unless `send_with_expired_token`; a failed refresh keeps the old token. Auth is applied after the
  auto headers (API key, OAuth token, AWS signing last); Digest sends, reads a 401/403 challenge,
  answers once (cached challenge or typed advanced fields answer on the first request), stores the
  realm/nonce/opaque/nc in `state.json`, and logs the first exchange as its own console entry. Token
  values are masked in the console and logs like secrets. A `mac` token is not sent (the notice is
  in the token panel).
- AWS: `X-Amz-Content-Sha256` is added for S3 only (Postman's aws4 behaviour); the payload hash is
  always used in the canonical request. Applicable test-suite vectors: 20 of 34 — excluded are path
  normalisation (8, the SDK signs the path as sent), single path encoding of raw UTF-8/space
  (`get-utf8`, `get-space`, `get-special-character`: the SDK double-encodes as AWS services expect),
  line folding (`get-header-value-multiline`), repeated header names (`get-header-key-duplicate`,
  `get-header-value-order`: Xenon sends one header per name), `get-vanilla-query-order-encoded`
  (the SDK sorts by decoded key) and `post-sts-header-after` (the token is always signed). Content
  length is not signed.
- T014 UI lives in a new `features/auth/` (store + `AuthEditor`, `ApiKeyForm`, `OAuth2Form` with
  `OAuth2Params`, `TokenPanel`, `AwsV4Form`, `DigestForm`) instead of
  `request-builder/components/auth/`: the same editor serves requests and collection/folder settings,
  so the app composes it into both (`app/layout/RequestAuth`, `app/layout/ItemAuth`) through the
  builder's `auth` slot and the settings form's `authEditor` slot. `ExpiredTokenDialog` offers
  "Get New Access Token" (opens the Authorization tab) and "Send Anyway".

  for secrets); session cookies are never written; a locked, undecided or needs-passphrase vault
  keeps the cookies in memory, and the next cookie call after unlock merges the file and writes.

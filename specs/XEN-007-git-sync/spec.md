# Feature Specification: Git Sync (Stage 7)

**Feature Branch**: `xen-007`

**Created**: 2026-10-09

**Status**: Draft

**Input**: User description: "Xenon Stage 7 — Git sync: each workspace optionally linked to its own Git repository (GitHub or any host) with any of the user's Git accounts; status, commit/push/pull, auto options, per-request conflict choices, clone a repo as a new workspace. Source: docs/prd/xenon-mvp-prd.md 'Git sync'; builds on XEN-001..006."

## Context

Stage 7 of 7. Workspaces are plain files (stage 1) so they could already be committed by hand;
this stage puts Git inside Xenon so each company's collections live in that company's repo,
with any mix of Git accounts, and teammates' changes come in with a Pull. Secrets, tabs and
layout never sync (they are local by design since stages 1–2).

## Clarifications

### Session 2026-10-09

- Q: A workspace in a subfolder of a repo the developer also has checked out — use that
  checkout or a separate clone? → A: Xenon keeps its **own clone per workspace** (only the
  workspace's subfolder is checked out); it never touches the developer's own checkouts and never
  pushes their unrelated commits.
- Q: Sign-in methods? → A: GitHub browser sign-in (device code), personal access tokens for any
  host, and SSH keys (existing keys, agent, or a key generated by Xenon).

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Link a workspace to a repo and sync daily (Priority: P1)

Luis links the Acme workspace to `github.com/acme/backend`, branch `main`, subfolder
`api/xenon`, using his GitHub account. The footer shows the sync status. When he changes requests,
the Sync panel lists them; he writes a message, commits and pushes. When teammates push, he pulls
and their changes appear.

**Why this priority**: This is the sync loop the stage exists for.

**Independent Test**: Against a test remote, link a workspace, change a request, commit and push,
make a remote change from another clone, pull, and verify both sides.

**Acceptance Scenarios**:

1. **Given** a workspace with no repo, **When** Luis opens its settings → Sync and enters repository
   URL, branch, optional subfolder and picks an account, **Then** Xenon prepares its own clone of
   that repo (checking out only the subfolder) and the workspace from then on lives in that
   subfolder; if the subfolder already contains a Xenon workspace he chooses "Use the repo's
   workspace" or "Replace it with mine"; if it is empty or missing, his workspace files are added
   there.
2. **Given** a linked workspace, **Then** the footer shows one of: Up to date, Local changes
   (n), Ahead (n to push), Behind (n to pull), Conflict, Error — and refreshes after saves, pulls,
   pushes and periodically (every 5 minutes, and on window focus).
3. **Given** local changes, **When** Luis opens the Sync panel, **Then** it lists changed requests,
   folders, collections and environments by name (added / modified / deleted / renamed), each with
   a checkbox (all checked), a commit message box, and Commit, Commit and Push, Push and Pull
   buttons.
4. **Given** he commits and pushes, **Then** only the checked items are committed (under the
   subfolder only), the commit is pushed to the branch, and the status becomes Up to date.
5. **Given** a teammate pushed changes, **When** Luis pulls, **Then** their changes appear in the
   sidebar and open clean tabs reload (XEN-001 FR-017 behaviour); his own uncommitted changes are
   kept.
6. **Given** both sides changed different requests, **When** Luis pulls, **Then** both sets of
   changes end up in the workspace without any prompt, and his local commits are replayed on top
   of the remote (linear history).
7. **Given** the workspace has no repo, **Then** everything works offline as before; sync is
   optional.

### User Story 2 - Resolve conflicts per request (Priority: P1)

When Luis and a teammate changed the same request, pulling shows the affected requests; for each
he chooses Keep mine, Keep theirs, or Keep both (theirs saved as a copy). No line-by-line editor.

**Why this priority**: Without it, the first concurrent edit blocks sync.

**Independent Test**: Create conflicting edits (same request, edit vs delete, same environment,
folder order) from two clones and resolve each kind.

**Acceptance Scenarios**:

1. **Given** the same request changed on both sides, **When** Luis pulls, **Then** the Conflict
   view lists it with both versions side by side (read-only, rendered as the request), and he picks
   Keep mine / Keep theirs / Keep both; Keep both saves theirs as a new request "<name> (theirs)"
   next to his.
2. **Given** a request deleted on one side and modified on the other, **Then** the choices are
   Keep (the modified version) or Delete.
3. **Given** an environment changed on both sides, **Then** the same three choices apply (Keep both
   creates "<name> (theirs)").
4. **Given** collection/folder/workspace settings files changed on both sides (e.g., both added
   requests to the same folder), **Then** non-overlapping changes merge automatically (order lists
   combined: theirs first, then my additions); only a field changed differently on both sides asks
   Keep mine / Keep theirs.
5. **Given** all conflicts are resolved, **When** Luis clicks Finish, **Then** the result is
   committed on top of the remote and he can push; Cancel leaves his workspace exactly as before
   the pull.

---

### User Story 3 - Git accounts (Priority: P1)

Luis adds his Git accounts once in app settings — his personal GitHub via browser sign-in, a
company GitLab with a token, an SSH key — and each workspace picks which account to sync with.

**Why this priority**: Nothing syncs without credentials; four companies mean several accounts.

**Independent Test**: Add one account of each kind, link three workspaces to repos on different
hosts and organisations with different accounts, sync each.

**Acceptance Scenarios**:

1. **Given** "Add GitHub account", **Then** Xenon shows a code and opens github.com/login/device;
   after Luis approves, the account (username, avatar, email) appears; the token is stored in the
   OS keychain (passphrase fallback per XEN-002), never in workspace files or the clone's config.
2. **Given** "Add token account", **Then** he enters host (e.g., gitlab.acme.test), username where
   needed, and token; Xenon verifies it against the host and stores it like above.
3. **Given** "Add SSH key", **Then** he picks an existing key file (with passphrase if
   encrypted), uses the SSH agent, or lets Xenon generate a new ed25519 key and shows the public
   key to copy (and, for a GitHub account, offers to add it to GitHub).
4. **Given** the first connection to an SSH host, **Then** Xenon shows the host key fingerprint
   for confirmation (GitHub, GitLab.com and Bitbucket keys are pre-trusted) and remembers it.
5. **Given** accounts, **Then** any workspace can use any account; one account may serve several
   workspaces and repos across organisations; commits use the account's name and email (editable
   per account).
6. **Given** an account is removed, **Then** workspaces using it show "No account — choose one" in
   the Sync panel.

---

### User Story 4 - Clone a repo as a new workspace (Priority: P2)

Luis joins a project: he pastes the repo URL, picks branch, subfolder, account and a local folder,
and gets a ready workspace.

**Why this priority**: The fastest way to onboard a company workspace; linking (US1) covers it
manually.

**Independent Test**: Clone a test repo with an existing workspace subfolder; open it; secrets
show as missing.

**Acceptance Scenarios**:

1. **Given** "New workspace from Git repository", **When** Luis enters URL, branch (default
   remote default branch), subfolder and account and picks where to keep it, **Then** Xenon clones,
   opens the workspace and makes it active.
2. **Given** the subfolder has no Xenon workspace, **Then** a new empty workspace is created there
   (commit offered).
3. **Given** the workspace has secret variables, **Then** they show as missing (values never
   travel in Git).

---

### User Story 5 - Automatic pull and push (Priority: P3)

Per workspace, Luis can turn on "Pull when the workspace is opened" and "Push after each save".

**Why this priority**: Comfort for solo repos; manual sync covers everything.

**Independent Test**: Enable both, switch workspaces and save requests; check remote and local.

**Acceptance Scenarios**:

1. **Given** auto-pull, **When** the workspace is opened or switched to, **Then** Xenon pulls in
   the background; if a conflict arises, the status shows Conflict and nothing changes until he
   resolves it.
2. **Given** auto-push, **When** he saves, **Then** after 3 seconds without further saves Xenon
   commits the saved items with message "Update <item names>" and pushes; failures show in the
   Sync panel without interrupting work.

---

### Edge Cases

- **No network / host unreachable**: status Error with "Offline — will retry"; commits still work
  locally; push/pull retried on demand.
- **Expired or revoked token / denied access** (including GitHub organisations that have not
  approved Xenon's OAuth app or SSO authorisation): message says which, with the next step
  (re-sign in, approve the app in the organisation, or use a token).
- **Push rejected because the remote moved**: Xenon pulls (replaying local commits), then pushes;
  if that creates conflicts, the Conflict view opens.
- **Push rejected by branch protection / required signed commits / hooks**: the error is shown;
  Xenon notes that it does not run Git hooks or sign commits.
- **Large File Storage** configured for the subfolder: linking is refused with an explanation.
- **Branch deleted on the remote**: status Error with options to pick another branch.
- **Uncommitted local changes when pulling**: kept; if an incoming change touches a file with
  uncommitted local edits, it is treated as a conflict for that item.
- **Files outside the subfolder** are never checked out, committed or shown.
- **Hand edits by other tools in the workspace folder** are picked up as local changes (XEN-001
  watcher).
- **Concurrent operations**: one sync operation at a time per workspace; buttons disabled while
  running, with progress.
- **Moving away from Git**: "Unlink repository" keeps the files (as a plain workspace folder copy
  at a location he picks) and deletes Xenon's clone after confirmation.
- **Line endings**: Xenon writes LF; files with CRLF from the remote are read normally (XEN-001).

## Requirements *(mandatory)*

### Functional Requirements

**Linking and cloning**

- **FR-001**: A workspace's Sync settings MUST hold repository URL, branch and optional subfolder
  (stored in `workspace.yaml` → `sync`, shareable) and the chosen account plus auto-pull/auto-push
  options (local only).
- **FR-002**: Xenon MUST keep its own clone per linked workspace with only the subfolder checked
  out; the workspace folder is that subfolder. Xenon MUST NOT operate on any other checkout.
- **FR-003**: Linking an existing workspace MUST clone the repo to a location Luis picks (default:
  Xenon's app data), then either adopt the repo's workspace or place his workspace files in the
  subfolder (and offer the first commit); the registry points to the new location and the old
  folder is left untouched (Luis is told where it is).
- **FR-004**: "New workspace from Git repository" MUST clone and open a workspace from URL, branch
  (default: remote default branch), subfolder, account and location; an empty subfolder becomes a
  new workspace.
- **FR-005**: Linking MUST be refused for repositories using Large File Storage within the
  subfolder, with an explanation.

**Status, commit, push, pull**

- **FR-006**: The footer MUST show the current workspace's sync status (Up to date, Local changes
  n, Ahead n, Behind n, Conflict, Error, Syncing) and refresh after saves/sync operations, every 5
  minutes and on window focus.
- **FR-007**: The Sync panel MUST list changed items by their Xenon names and kind (request,
  folder, collection, environment, workspace settings) with change type, checkboxes, a commit
  message (required), and Commit / Commit and Push / Push / Pull.
- **FR-008**: Commits MUST include only checked items under the subfolder, authored with the
  account's name and email.
- **FR-009**: Pull MUST fetch, then: fast-forward when possible; when both sides have commits,
  replay local commits on top of the remote (linear history), merging non-conflicting changes
  automatically; conflicting items go to the Conflict view (FR-011). Uncommitted local changes are
  preserved.
- **FR-010**: Push MUST push the branch only; if rejected because the remote moved, Xenon MUST pull
  (FR-009) and retry once; other rejections show the host's message.

**Conflicts**

- **FR-011**: Conflicts MUST be resolved per item: requests and environments → Keep mine / Keep
  theirs / Keep both (theirs copied as "<name> (theirs)" with a new id); delete vs modify → Keep /
  Delete; collection, folder and workspace settings files → automatic field-level merge (order
  lists combined, theirs first then my additions; non-overlapping fields merged) with Keep mine /
  Keep theirs only for fields changed differently on both sides.
- **FR-012**: The Conflict view MUST show both versions rendered as Xenon items (read-only), allow
  resolving in any order, and offer Finish (commit result) and Cancel (restore the exact pre-pull
  state).

**Accounts and credentials**

- **FR-013**: App settings MUST manage Git accounts: GitHub (browser sign-in with a device code),
  token accounts (any host: GitHub, GitLab, Bitbucket, Azure DevOps, self-hosted; host + optional
  username + token, verified on save), and SSH keys (existing key file with passphrase, SSH agent,
  or generated ed25519 with the public key shown and, for GitHub accounts, optional upload).
- **FR-014**: Tokens, key passphrases and generated private keys MUST be stored only in the OS
  keychain (or the XEN-002 passphrase-protected fallback) / owner-only key files in app data —
  never in workspace files, the clone's Git config or remote URLs.
- **FR-015**: SSH host keys MUST be verified: pre-trusted keys for github.com, gitlab.com and
  bitbucket.org; others confirmed by fingerprint on first use and remembered; a changed key blocks
  the connection with a warning.
- **FR-016**: Each workspace MUST be able to use any account; accounts can be removed; affected
  workspaces then ask for another.

**What is synced**

- **FR-017**: Only workspace files (collections, folders, requests, environments, workspace
  settings) under the subfolder are synced; secret values, current values, tabs, layout, history,
  cookies and tokens never are (they are not in the workspace folder). Xenon's `.gitignore` block
  stays in the workspace.

**Automation and errors**

- **FR-018**: Per workspace options "Pull when opened" and "Push after each save" (3 s debounce,
  auto message "Update <item names>") MUST run in the background and surface failures in the Sync
  panel.
- **FR-019**: Errors (offline, auth expired, organisation approval/SSO required, push rejected,
  branch missing, protected branch) MUST be shown in the Sync panel with a specific next step.
- **FR-020**: Only one sync operation per workspace runs at a time; the UI shows progress and
  disables conflicting actions.
- **FR-021**: "Unlink repository" MUST copy the workspace files to a folder Luis picks, re-point
  the workspace to it, and delete Xenon's clone after confirmation.

### Key Entities

- **Sync settings** (workspace.yaml `sync`): repository URL, branch, subfolder.
- **Local sync settings** (local): account id, auto-pull, auto-push, clone location.
- **Git account** (local + keychain): kind (github | token | ssh), display name, host, username,
  commit name/email, credential reference.
- **Sync status**: state, counts (local changes, ahead, behind), last sync time, last error.
- **Change item**: Xenon item (id, name, kind), change type, path(s).
- **Conflict item**: item, kind of conflict, mine/theirs/base versions, resolution.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: Commit-and-push of a typical change (1–10 requests) completes in under 5 seconds on
  a normal connection; pull with no conflicts in under 5 seconds.
- **SC-002**: In a two-user test with 100 random concurrent edits, 100% of non-conflicting changes
  merge without prompts and 100% of conflicting items appear in the Conflict view; no change is
  lost.
- **SC-003**: 0 secret values, tokens or local state ever appear in commits (verified on the test
  remote's history).
- **SC-004**: Xenon never modifies files outside its own clones (verified by checksumming a
  developer checkout of the same repo before and after a sync session).
- **SC-005**: Setting up sync for a new workspace from a repo URL takes under 2 minutes including
  sign-in.
- **SC-006**: All flows work on macOS, Windows and Linux with HTTPS tokens, GitHub sign-in and SSH.

## Assumptions

- Branch switching/creation, pull requests, history view and blame are out of the MVP (PRD).
- Xenon does not run Git hooks or sign commits; repos requiring them must be configured to allow
  Xenon's pushes or use a separate branch.
- GitHub browser sign-in requires a GitHub OAuth App (device flow enabled) registered by the
  project owner; its client id ships with Xenon (no secret, no server). **Owner: Luis — register
  the app before implementation of US3 starts** (blocks only GitHub browser sign-in; tokens and
  SSH work without it).
- Organisations that restrict OAuth apps must approve Xenon's app (or Luis uses a token account
  for them).

# Frontend Architecture — React + TypeScript in Wails v3

The frontend is a **thin client**. Go does all real work (HTTP, scripts, disk, secrets, git);
React only displays and edits. This skill is the frontend's equivalent of `architecture.md`:
every file has one right place, and dependencies flow one way. **These rules are law** — same
weight as the backend skills.

Use together with:
- `vercel-react-best-practices` — performance rules (re-renders, bundle, JS). Skip the
  `server-*`, `async-api-routes`, `rendering-hydration-*` and Next.js-specific rules: this is a
  client-only SPA in a desktop webview, there is no server rendering.
- `vercel-composition-patterns` — component API design (compound components, no boolean-prop
  sprawl, explicit variants).
- `vercel-web-design-guidelines` — UI/a11y review checklist.

## Directory structure

```
frontend/
├── index.html
├── package.json
├── vite.config.ts
├── tsconfig.json
├── eslint.config.js             ← enforces the import boundaries below
├── bindings/                    ← GENERATED by `wails3 generate bindings`. Never edit. Git-ignored.
├── public/
│   └── fonts/                   ← Inter, JetBrains Mono, marker display font (self-hosted)
└── src/
    ├── main.tsx                 ← mounts <App/>; nothing else
    │
    ├── app/                     ← COMPOSITION ROOT — wires features into the window
    │   ├── App.tsx
    │   ├── layout/              ← the window regions (PRD "Screen layout")
    │   │   ├── AppShell.tsx         top bar · sidebar · main · right panel · console · footer
    │   │   └── regions/             TopBar, Footer, MainArea… (place features, own no logic)
    │   ├── hotkeys.ts           ← global hotkey table (PRD "Hotkeys") → feature actions
    │   └── bootstrap.ts         ← startup: load workspace list, subscribe to backend events
    │
    ├── features/                ← ONE FOLDER PER PRODUCT AREA (vertical slices)
    │   ├── workspaces/          ← switcher, create/rename/delete, per-workspace UI state
    │   ├── sidebar/             ← collection tree, search, drag & drop, context menu
    │   ├── tabs/                ← tab strip, preview vs pinned, dirty dot, tab context menu
    │   ├── request-builder/     ← request bar, Params/Auth/Headers/Body/Scripts/Settings sub-tabs
    │   ├── response-viewer/     ← status line, Body/Cookies/Headers/Test Results
    │   ├── environments/        ← switcher, quick look, environment editor, secrets display
    │   ├── console/             ← bottom drawer, log entries, filters
    │   ├── side-panel/          ← Variables / Code / Info panels
    │   ├── import-export/       ← dialogs, summaries
    │   ├── sync/                ← Sync panel, footer status, conflict resolution
    │   ├── cookies/             ← cookie jar dialog
    │   └── settings/            ← settings page, Git accounts, shortcut list
    │
    │   Each feature folder has the same internal shape (create only what you need):
    │   features/<feature>/
    │   ├── components/          ← React components for this feature (PascalCase.tsx)
    │   ├── hooks/               ← feature hooks (use-*.ts)
    │   ├── store.ts             ← the feature's Zustand store (state + actions)
    │   ├── model.ts             ← the feature's TypeScript types
    │   ├── lib/                 ← pure functions (no React, no store, no platform)
    │   └── *.test.ts(x)         ← colocated tests
    │
    ├── platform/                ← THE ONLY DOOR TO GO — wraps Wails bindings + runtime
    │   ├── services/            ← one file per Go service: workspaces.ts, requests.ts,
    │   │                           environments.ts, vault.ts, sync.ts, import-export.ts …
    │   ├── events.ts            ← typed subscriptions to backend events (Events.On)
    │   ├── errors.ts            ← maps Go errors to a single AppError type
    │   └── mappers/             ← binding DTO ⇄ frontend model conversion
    │
    └── shared/                  ← DOMAIN-FREE building blocks
        ├── ui/                  ← design system: Button, IconButton, Tabs, Dropdown, Dialog,
        │                           ContextMenu, SplitPane, KeyValueTable, CodeEditor,
        │                           MethodBadge, EmptyState, Tooltip … (one folder each)
        ├── hooks/               ← generic hooks: use-hotkey, use-resizable, use-disclosure
        ├── lib/                 ← generic helpers: format-bytes, format-duration, cn …
        ├── styles/
        │   ├── tokens.css       ← PRD palette, method colours, glow, spacing, radii, fonts
        │   ├── global.css       ← reset + base typography
        │   └── fonts.css
        └── types/               ← generic utility types only
```

### Why this shape

- **Vertical slices (`features/`)** — everything about "tabs" lives in one folder, so a change to
  a feature touches one place. The list of folders mirrors the PRD sections, which mirror the
  Go services.
- **`platform/` is an anti-corruption layer** — the same idea as backend adapters. Generated
  bindings change whenever Go changes; only `platform/` absorbs that. Components never know
  Wails exists, so they stay testable with plain mocks.
- **`shared/` knows nothing about Xenon** — a `KeyValueTable` works on rows, not on "headers".
  Domain meaning is added by the feature that uses it.
- **`app/` composes** — only `app/` places several features next to each other. Features don't
  assemble the window.

## Dependency rules (enforced by ESLint)

```
app ──► features ──► platform ──► bindings / @wailsio/runtime
  │         │   └──► shared
  │         └──────► other feature's store.ts (selectors/actions ONLY)
  └──► shared, platform
platform ──► shared (types/lib only)
shared ──► nothing in src/ except shared
```

| From \ may import | `app/` | `features/x` | `features/y` | `platform/` | `shared/` | `bindings/`, `@wailsio/runtime` |
|---|---|---|---|---|---|---|
| `app/` | ✅ | ✅ | ✅ | ✅ | ✅ | ❌ |
| `features/x` | ❌ | ✅ (own) | `store.ts` only | ✅ | ✅ | ❌ |
| `platform/` | ❌ | ❌ | ❌ | ✅ | ✅ | ✅ (**only here**) |
| `shared/` | ❌ | ❌ | ❌ | ❌ | ✅ | ❌ |

Rules:

1. **Only `platform/` imports `frontend/bindings/**` or `@wailsio/runtime`.** Anything else that
   needs Go calls a `platform/services/*` function.
2. **A feature never reaches into another feature's `components/`, `hooks/`, `lib/` or
   `model.ts`.** It may read/act on another feature's state through that feature's `store.ts`
   (e.g. `request-builder` reads the active environment from `environments/store.ts`). If two
   features need the same component, it either moves to `shared/ui/` (if domain-free) or the
   composition happens in `app/`.
3. **`shared/` never imports from `features/`, `platform/` or `app/`.**
4. **No barrel files** (`index.ts` re-exporting a folder). Import the file directly
   (`vercel-react-best-practices` → `bundle-barrel-imports`). This also keeps the boundary
   rules visible in every import line.
5. Use the `@/` path alias for `src/` (`@/shared/ui/button/Button`). Relative imports only
   within the same feature/folder.

Enforce with `eslint-plugin-boundaries` (or `import/no-restricted-paths`) in
`eslint.config.js`; a boundary violation is a lint error, not a review comment.

## Talking to Go (`platform/`)

```ts
// platform/services/requests.ts
import { RequestService } from '../../bindings/github.com/brienze1/xenon/internal/integration/entrypoint/controller'
import { toSendResult, type SendResult, type SendInput } from '../mappers/request'
import { toAppError } from '../errors'

export async function sendRequest(draft: SendInput): Promise<SendResult> {
  try {
    return toSendResult(await RequestService.Send(draft))
  } catch (err) {
    throw toAppError(err)
  }
}
```

- Types that cross the bridge are defined in `platform/` (or `shared/types`), **not** imported
  from features — `platform` must not depend on `features`. Features import those types from
  `platform/`.
- Every Go call goes through a function here that: calls the binding, maps the DTO, and converts
  errors to `AppError`. Components and stores never see raw binding types.
- Long-running calls (Send, Pull, Push, Import) keep the cancellable promise the binding returns
  so the UI can offer Cancel (PRD: Send ↔ Cancel).
- **Backend → UI pushes** (console entries, sync status, file changes) arrive as Wails events.
  `platform/events.ts` exposes typed `onConsoleEntry(cb)`, `onSyncStatus(cb)` … wrappers around
  `Events.On` that return the unsubscribe function. Event names are constants shared with Go —
  one place per side, never string literals scattered in components.
- Subscriptions are opened once in `app/bootstrap.ts` and pushed into stores, not in random
  components (`vercel-react-best-practices` → `client-event-listeners`).

## State (Zustand)

- **Go is the source of truth** for anything persisted (workspaces, collections, requests,
  environments, open tabs, layout sizes — the PRD says these are remembered per workspace, and
  Go owns the disk). Stores hold a working copy plus UI-only state.
- **One store per feature**, in `features/<feature>/store.ts`. No global mega-store.
- Actions live in the store and call `platform/` — components call actions, never `platform/`
  directly for writes.
- Select narrowly: `useTabsStore(s => s.activeTabId)`, never `useTabsStore()` whole
  (`rerender-derived-state`, `rerender-defer-reads`). Use `useShallow` for multi-field selects.
- Derive, don't duplicate: computed values are selectors or computed during render, not extra
  state synced with effects (`rerender-derived-state-no-effect`).
- **No `localStorage` for product state.** Workspace-scoped UI state is persisted through Go so
  it follows the workspace. `localStorage` only for throwaway per-machine preferences, if ever.
- Workspace switch is a hard boundary (PRD): every workspace-scoped store exposes `reset()` and
  `workspaces/store.ts` calls them on switch before loading the new workspace.

## Components

- **Component files**: `PascalCase.tsx`, one exported component per file, named like the file.
  Other files: `kebab-case.ts`. Hooks: `use-thing.ts` exporting `useThing`.
- Props typed with an `interface <Name>Props` above the component. No `React.FC`.
- Follow `vercel-composition-patterns`: compound components (`<Tabs.List>`, `<Tabs.Panel>`)
  instead of boolean props; explicit variant props (`variant="primary"`) instead of
  `isPrimary`/`isGhost`.
- Never define components inside components (`rerender-no-inline-components`).
- Conditionals render with ternaries, not `&&` on numbers (`rendering-conditional-render`).
- Long lists (sidebar tree, console, large response bodies) are virtualized; large bodies open
  in Raw first (PRD).
- Heavy modules (CodeMirror languages, response Preview) load with dynamic `import()` when first
  needed (`bundle-dynamic-imports`, `bundle-conditional`).
- Accessibility is not optional: every icon button has an `aria-label`, menus/dialogs are
  keyboard-navigable, focus rings use the cyan token. Run `vercel-web-design-guidelines` on new
  UI.

## Styling

- **CSS Modules** (`Component.module.css`) next to the component, plus global design tokens.
  No inline style objects except for truly dynamic values (sizes from a drag).
- `shared/styles/tokens.css` is the **only** place hex colours appear. It defines the PRD palette
  as CSS variables — `--color-bg`, `--color-surface`, `--color-surface-raised`, `--color-border`,
  `--color-text`, `--color-text-muted`, `--neon-green`, `--neon-cyan`, `--neon-magenta`,
  `--neon-yellow`, `--neon-red`, the HTTP method colours `--method-get` …, glow shadows
  `--glow-green` …, spacing/radius scales and font stacks (`--font-ui: Inter`,
  `--font-mono: JetBrains Mono`, `--font-display` for the marker font).
- Neon is for accents and state only, never body text. Glow only on active/attention elements
  (PRD "Neon and shadow rules"). Panels separate by depth/shadow, not bright borders.
- Dark theme only; still route every colour through tokens so a light theme stays possible.

## Hotkeys

- One table in `app/hotkeys.ts` maps PRD shortcuts to store actions; `Cmd` is normalised to
  `Ctrl` on Windows/Linux by `shared/hooks/use-hotkey.ts`.
- Features never register global keydown listeners themselves. Scoped shortcuts (e.g. Cmd+F in
  the response body) use `use-hotkey` with a scope/element.
- The Settings shortcut list renders from the same table — one source of truth.

---

## Testing

- **Vitest + React Testing Library**, tests colocated as `*.test.ts(x)`.
- Test stores and `lib/` functions directly; test components through user behaviour
  (roles, labels), not implementation details.
- Mock **`platform/`**, never the generated bindings — that's why `platform/` exists.
- Business behaviour (sending, scripts, storage, secrets, sync) is covered by the Go BDD suite;
  frontend tests cover UI state and interaction.
- Gate: `npm run lint && npm run typecheck && npm test` must be green, alongside `make validate`.

## Checklist — where does this go?

| I'm writing… | Put it in |
|---|---|
| A call to a Go service | `platform/services/<service>.ts` |
| Listening to a backend event | `platform/events.ts` + subscribe in `app/bootstrap.ts` |
| A generic, domain-free UI piece | `shared/ui/<name>/` |
| A UI piece that knows about requests/envs/tabs… | `features/<feature>/components/` |
| State for a product area | `features/<feature>/store.ts` |
| A pure helper used by one feature | `features/<feature>/lib/` |
| A pure helper used everywhere | `shared/lib/` |
| Placing features into the window | `app/layout/` |
| A global shortcut | `app/hotkeys.ts` |
| A colour, glow, font, spacing value | `shared/styles/tokens.css` |
